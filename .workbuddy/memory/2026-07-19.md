  4. 房间号 `trim()` 防手滑空格导致两端房间号不一致。

## 修复:原生端连不上对方——真正根因是"注册消息缺失"(非信令 to 字段)
- 现象反复出现:web 版(web_client.html)能互通,但原生 exe/APK 进同一房间后两端都卡"等待对方加入",看不到对方。前几轮(run3~run6)的修复(自动呼叫/广播对齐 web)都没解决,因为根因根本不在 WebRTC 协商层。
- **真正根因**:信令服务器 `signaling_server.py` 的 `handle_connection` 第一步 `await asyncio.wait_for(websocket.recv(), timeout=10.0)` 要求客户端连上后**立即发一条带 userId 的消息**,否则 10 秒超时 `close(4003)`。原生端 `SignalingService.connect()` 只建 WebSocket 连接、**不发任何注册消息**。用户从"连接服务器"到手动"进入房间"常超 10 秒,此时服务器已关连接,`joinRoom` 的消息发不出去(或首条 join 被当注册消费后入房状态异常)→ 双方都"假进房、真等待"。
- **关键差异证据**:web 版 `web_client.html:291-294` 在 `ws.onopen` 里**立即 `ws.send({userId:myId})`** 再发 join,所以永远踩不到超时。原生端缺这步。
- **对照实验(铁证)**:用 Python websockets 脚本模拟两个客户端连同一服务器房间:
  - 旧模式(A 首条消息=join,不发 register):B 加入时回执 `members=['verB']`,A 收不到 B 广播 → **互不可见**(复现用户现象)。
  - 新模式(都先发 register 再 join):A 立即收到 `join from=verB` 广播,B 回执 `members=['verA','verB']` → **互相发现**。
- 修复:
  - `lib/services/signaling_service.dart`:`connect(url,{userId})` 在 `ready` 后**立即 `send(SignalMessage(type:'register',from:userId))`**(对齐 web),并启动 `Timer.periodic(20s)` 发 `ping` 心跳保活;dispose 取消 timer。
  - `lib/viewmodels/call_viewmodel.dart`:`connect` 传 `userId:_currentUserId` 给 `signaling.connect`。
  - 同时加**屏幕调试日志面板**:vm 维护 `_debugLog`(带时间戳),在 connect/join/发现对端/收发明文 offer/answer/candidate/ICE状态/收到轨道 等关键节点 `_logDebug`;WebRTCService 加 `onLog` 回调(ICE状态/收发offer/answer/收到轨道),由 vm 注入;CallPage 右上角加 `bug_report` 图标,点开 `StatefulBuilder` 对话框反转显示日志(带"刷新")。便于后续若仍异常,用户直接看日志定位,免来回盲猜。
- 验证:`flutter analyze` No issues found。offline 信令层对照实验证明修复后双方可互相发现。双端重编 EXIT=0:
  - Windows exe:后台 6HsGjL(`build_windows_run7.log`,EXIT=0)。
  - Android APK:后台 BnNjmZ(`build_apk_run7.log`)。
- 注意:仍为同一局域网限制(STUN-only,无 TURN);跨公网需加 TURN 服务器。若仍连不上,让用户在 CallPage 点右上角 bug 图标看调试日志,把"发送 join/收到 join回执members/发现对端/发送或收到 OFFER/ICE 状态"这几行发来即可定位。

## 修复:"已联通但无视频画面"(信令成功、媒体不通)
- 现象:用户装 run7 包实测,两端都显示"通话已连接"(onCall),但双方都看不到对方的视频画面。
- 关键认知:**onCall 状态只是在"收到/发出 offer-answer"时就置位,并不代表媒体真正在流动**;只要信令能互换 SDP,状态就变绿,所以"联通但黑屏"是典型媒体协商/ICE 问题,不是信令问题。
- **真正根因**:`webrtc_service.dart` 旧逻辑在 `createAndSendOffer`/`receiveOfferAndAnswer` 里**等 ICE 收集满(最长 10s)才发送 offer/answer**(`_waitForIceGatheringComplete().then(...)`)。在这 10s 内,本端 `onIceCandidate` 已经把 candidate 广播到房间,但**对方此时还没建连**(对方要等收到 offer/answer 才 `_createPeerConnection`),于是这些 candidate 被丢弃;等对方终于收到 offer 建连后,本端早该发的 candidate 已丢失 → 双方 ICE 无法汇合 → 媒体通道建立失败 → 无画面(但信令层"connected"早已置位)。
- 修复(改为标准 trickle ICE):
  1. `createAndSendOffer`/`receiveOfferAndAnswer`:`setLocalDescription` 后**立即** `sendOffer/sendAnswer`,不等 ICE 收集;candidate 仍由 `onIceCandidate` 在 `signaling.sendCandidate` 中逐个 trickle 补发。
  2. `receiveCandidate`:包 try/catch,容忍 candidate 早于 `setRemoteDescription` 到达(忽略异常,后续 candidate 仍会补到)。
  3. 删除已无用的 `_waitForIceGatheringComplete()`。
  4. 新增 `hasConnection` getter;`call_viewmodel._initiatePeerConnection` 加守卫:若 `_webrtc.hasConnection` 已为真则跳过,**防止 8s 兜底重试把正在建立中的 PeerConnection 关掉重建**而打断协商。
- 验证:`flutter analyze` No issues found。双端重编(run8)完成:
  - Windows exe:后台 TuCWTo(EXIT=0)。
  - Android APK:后台 N3Wkf3(EXIT=0,81MB)。

## 修复:手机端无法自动识别服务器 IP(run15)

## 换方案:TCP 子网扫描作为主发现路径(run16 续5)

- **实测验证**:独立 dart 脚本在本机跑,736ms 扫到 `ws://10.220.63.242:8765`(本机前缀含 10.220.63./172.31.80./172.25.0.,Hyper-V 虚拟网卡也一并扫,不影响)。
